Deepfake Video Detection

A full-stack platform that takes a video upload, runs a ResNeXt50 + recurrent PyTorch model over face crops, and returns a REAL or FAKE verdict with confidence, frame statistics and a stored history.

Overview

The platform has three parts. A Spring Boot backend accepts the upload, stores the file, calls the ML service and persists the result in PostgreSQL; it also serves the web UI. A FastAPI ML service decodes the video, crops the largest frontal face in each sampled frame and scores the sequence with a ResNeXt50_32x4d backbone and a recurrent head. The web UI uploads with a progress bar, shows the verdict card, and lists every analysis with stats.

Request flow

  1. The browser posts the video as multipart/form-data to POST /api/analyses.
  2. DetectionService validates the extension, stores the file under a UUID name and calls MlClient.predict.
  3. The ML service picks SEQUENCE_LENGTH frames, crops the largest frontal face per frame with 15 % padding (centre square when no face is found), resizes to 112 × 112 RGB, normalises with ImageNet statistics and runs the model. Softmax over the two classes gives fake_probability and real_probability.
  4. The backend persists a video_analysis row, or an ERROR row if the ML call failed, and returns it.
  5. The UI renders the verdict card and refreshes the history table and stats tiles.

The ML call is deliberately outside any database transaction, so a slow video never pins a connection. If the ML service is down, the upload is still recorded with verdict ERROR and the client receives HTTP 502 with a JSON body.

Quick start

Prerequisites

  • Java 17 (the Maven wrapper ./mvnw downloads Maven itself).
  • Python 3.10 or newer.
  • PostgreSQL on localhost:5432, or Docker for the compose option.

Option A: one command

git clone <repository-url> deepfake-video-detection
cd deepfake-video-detection

# database, once
psql -h localhost -U postgres -c "CREATE ROLE deepfake LOGIN PASSWORD 'deepfake';"
psql -h localhost -U postgres -c "CREATE DATABASE deepfake_db OWNER deepfake;"

# python dependencies and a pretrained checkpoint
cd ml-service && python3 -m pip install -r requirements.txt -r requirements-dev.txt
python3 -m scripts.download_weights --frames 20
cd ..

./run-local.sh        # starts ML service (:8000) and backend + UI (:8080), Ctrl+C stops both

Open http://localhost:8080, drop a clip from docs/samples/ onto the upload box and press Analyze. The script detects a PostgreSQL server older than 12 and switches the backend to the legacypg profile automatically.

Option B: start the services yourself

# terminal 1: ML service
cd ml-service
uvicorn app.main:app --host 0.0.0.0 --port 8000

# terminal 2: backend + UI
cd backend
./mvnw spring-boot:run                       # PostgreSQL 12 or newer
SPRING_PROFILES_ACTIVE=legacypg ./mvnw spring-boot:run   # PostgreSQL older than 12

Option C: Docker Compose

docker compose up --build
# UI       http://localhost:8080
# ML docs  http://localhost:8000/docs

Compose starts PostgreSQL 16, builds both images and mounts ml-service/weights/ read-only into the ML container, so download a checkpoint first.

ML model

Each sampled frame goes through torchvision.models.resnext50_32x4d (ImageNet weights, final pooling and classifier removed) and becomes a 2048-dimensional feature vector. A recurrent layer with hidden size 2048 reads the sequence, followed by dropout 0.4 and a linear layer with two outputs. Class index 0 is FAKE, index 1 is REAL; the reported confidence is the softmax probability of the chosen class.

Architecture profiles

ProfileRecurrent layerPoolingFrame samplingUse
gruGRU, batch-first, with biasMean of GRU outputs over timeSpread evenly over the clipThis project's own model; train it with scripts/train.py
jadhav-lstmLSTM created as nn.LSTM(2048, 2048, 1, False), so bias=False and batch_first=FalsePer-frame logits averagedConsecutive frames from the first detected faceLoads the public ResNeXt50 + LSTM checkpoints unchanged

The public checkpoints were trained with an LSTM whose fourth positional argument was meant to be bidirectional but is actually bias, and without batch_first, so every frame is effectively scored on its own. The jadhav-lstm profile reproduces that exactly, which keeps the weights valid, and then averages the per-frame logits instead of trusting the last frame only.

Preprocessing

  1. Decode with OpenCV. For head sampling, scan the first three seconds for the first frame with a face and take SEQUENCE_LENGTH consecutive frames from there; for uniform sampling, spread the frames over the whole clip.
  2. Detect faces with the Haar frontal-face cascade on a copy downscaled to 640 px wide, keep the largest, add 15 % padding. Without a face, use the centre square.
  3. Resize to 112 × 112, convert to RGB, scale to 0–1 and normalise with ImageNet mean and standard deviation.
  4. Repeat the last frame when the clip is shorter than the sequence length.
On four real-world clips, the choice of RGB input, consecutive frames from the first face and 15 % padding was the only combination that separated real footage (≤ 0.15 fake probability) from face-swap deepfakes (≥ 0.99). BGR input or evenly spread frames made the deepfakes score REAL.

Weights

The service loads the first *.pt in ml-service/weights/. Without one it still starts, uses an ImageNet backbone with an untrained head, and reports trained: false; the UI then shows an amber "untrained demo weights" pill.

# pretrained checkpoint (226 MB), 20 frames, trained on FaceForensics++ / Celeb-DF / DFDC
python3 -m scripts.download_weights --frames 20
python3 -m scripts.download_weights --list      # see every checkpoint in the public folder

# train your own GRU model: DATA/{train,val}/{real,fake}/*.mp4
python3 -m scripts.train --data DATA --epochs 10 --seq-len 20 --out weights/deepfake_gru_20_frames.pt

Checkpoints are loaded with torch.load(..., weights_only=True), so a downloaded file cannot execute code. Training writes the profile, sequence length and image size into the checkpoint so the service configures itself from it.

Limitations

  • The public checkpoint learned face-swap deepfakes with a visible frontal face. Fully generated video, cartoons, or clips without a face are outside its training distribution and verdicts on them are not meaningful.
  • Its published accuracy (87 %) is on its own benchmark split. The sample clips here are a smoke test, not an evaluation.
  • The Haar cascade misses strongly turned faces; the centre-square fallback keeps the pipeline running but lowers confidence.

Testing

cd backend && ./mvnw test          # 18 tests: MockMvc controller tests on H2 with the ML client mocked,
                                   # plus RestClient wire-format tests against MockRestServiceServer
cd ml-service && python3 -m pytest # 5 tests: health, model info, prediction on a synthetic clip,
                                   # unsupported extension (400), undecodable video (400)

The backend tests run on an in-memory H2 database in PostgreSQL mode, so they need neither PostgreSQL nor the ML service. The ML tests generate their own one-second clip and run the real model on CPU; set SEQUENCE_LENGTH=6 (the tests do this) to keep them under five seconds.

Deployment

Containers

backend/Dockerfile is a two-stage build (Maven with Temurin 17, then a slim JRE) that produces an image running java -jar app.jar with uploads under /app/uploads. ml-service/Dockerfile installs CPU wheels of PyTorch from the official index and serves with Uvicorn on port 8000. docker-compose.yml wires both to PostgreSQL 16 with health checks and named volumes for the database and uploads.

Before exposing it publicly

  • Put the backend behind HTTPS and add authentication; the API currently has none and CORS is open on /api/**.
  • Set APP_STORAGE_DIR to a persistent absolute path, or swap StorageService for object storage.
  • Give the ML service a GPU (DEVICE=cuda) or more CPU; one prediction takes 2 to 4 s of CPU time and requests are processed one at a time per worker.
  • Lower MAX_UPLOAD_MB and the backend's multipart limits to what you actually need.
  • Change the database password and keep it out of docker-compose.yml (use an env file or secrets).
